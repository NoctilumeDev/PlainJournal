# 素简记分布式电商平台项目计划书

> 项目英文标识：Plain Journal  
> 项目类型：自营 B2C 起步、面向分布式与高并发能力成长、可演进至多商户的平台型电商  
> 当前版本：V1.0  
> 基线日期：2026-07-16  
> 当前坐标：营销价格基础已完成，下一阶段为整单退货退款

## 1. 执行摘要

素简记不是对既有商城的界面复刻，也不是为了展示中间件数量而搭建的微服务样板。它以一条真实、完整、可核对的自营 B2C 交易链为业务载体，在个人单机环境能够承受的范围内，系统性实践从增强型单体走向分布式业务系统、多实例集群、高并发系统、数据规模化和多商户平台的关键机制。

项目首先保证交易事实正确：订单、库存、支付、履约、营销和退款均以 MySQL 为最终事实；跨服务不依赖分布式大事务，而使用本地事务、Outbox、RocketMQ、幂等消费、状态机、补偿和对账实现最终一致性。随后通过多实例部署、故障注入、链路观测和量化压测，证明系统在重复消息、乱序、超时、进程退出、中间件故障和热点并发下仍然可解释、可恢复、不超卖、不重复扣款或退款。

前端与后端遵循相反但互补的复杂度原则：后端承担分布式复杂性，前端只向用户呈现清晰、确定、可信的商品与交易状态。素简记的视觉语言从零建立，不继承任何既有项目的前端样式，目标是现代、干净、耐看、克制、高级但不冷漠。

项目总原则是：

> 把复杂留给系统，把简单交给用户。

## 2. 项目缘起与技术成长主线

### 2.1 已完成的单体能力

此前的图书管理系统已经覆盖完整单体应用常见能力，包括 Spring Boot、Vue 3、MySQL、本地事务、JWT/RBAC、Redis 缓存、RabbitMQ、定时任务、文件生命周期、JUnit/H2 和前端 E2E。

素简记不重复证明这些基础能力，而是重点处理系统拆开以后出现的新问题：

- 服务拥有独立数据，不能跨库 JOIN 或依赖单个本地事务。
- 网络调用可能超时，但下游可能已经成功。
- 消息可能重复、延迟、乱序或暂时无法发送。
- 多实例可能同时处理同一业务命令、消息和定时任务。
- 中间件故障不能伪造业务成功，也不能永久卡死。
- 缓存、队列和分片只能提高容量，不能改变最终事实归属。
- 平台扩展到多商户后，订单、优惠、履约、售后和资金都需要重新明确经营主体。

### 2.2 能力阶梯

```text
增强型单体
  -> 分布式业务系统
  -> 多实例集群
  -> 生产型服务治理
  -> 高并发交易系统
  -> 数据规模化
  -> 多商户平台
  -> 实时与智能化系统
```

个人电脑无法复刻大型互联网平台的节点数量和流量规模，但可以缩小规模、保持问题类型不变：启动多个实例、制造延迟和断连、重复和打乱消息、制造 MQ 积压、生成百万到千万级数据、验证缓存击穿和热点库存竞争，并记录可重复的吞吐、延迟与恢复结果。

因此，本项目追求的是“机制真实、证据真实、规模缩比”，不宣称复刻任何大型平台。

## 4. 核心架构原则

### 4.1 事实与一致性

1. MySQL 是最终事实，缓存和消息不能覆盖数据库裁决。
2. 单服务内使用本地事务，跨服务不使用 2PC、TCC 或跨库大事务。
3. 业务状态更新和 Outbox 插入必须在同一本地事务中完成。
4. 消费幂等记录和业务副作用必须在同一本地事务中完成。
5. 任何重试都必须建立在稳定业务编号、幂等键或数据库唯一约束上。
6. 超时只代表结果未知，不代表失败；调用方必须能够查询或恢复。
7. 支付、退款、库存流水、价格快照和审计事实不可被普通更新接口覆盖。

### 4.2 服务与数据所有权

- Gateway 负责入口治理，不承载业务规则或访问业务数据库。
- Identity 负责用户、地址、令牌和权限。
- Catalog 负责商品定义与媒体，不负责库存数量和历史订单价格。
- Inventory 负责仓库、现货、预占、释放、确认与回补流水。
- Trade 负责购物车、订单、价格快照、订单状态和售后聚合。
- Payment 负责支付单、回调、退款单、渠道流水和对账。
- Fulfillment 负责正向履约、物流轨迹、退货收货和仓库验收。
- Marketing 负责规则、权益、定价锁和权益生命周期。
- Chat 与 Notification 在后续阶段分别负责实时会话和通知投递。

服务之间只能通过 DTO、内部 API 和版本化事件协作，禁止共享数据库 Entity、跨 schema 外键和跨服务 Mapper。

### 4.3 复杂度准入

学习目标允许适度超前引入技术，但每项复杂度必须回答：

1. 它解决了旧项目没有实践过的什么问题？
2. 它由哪个真实业务场景承载？
3. 不引入时可以复现什么失败或瓶颈？
4. 引入后通过什么自动测试、故障测试或压测证明有效？
5. 如何限制影响范围并支持回退？

不以接入某个框架或中间件作为完成标准，以正确性、恢复性、可观测性和量化结果作为完成标准。

## 9. 里程碑路线

### M0：分布式正向交易基线

状态：已完成。

交付包括8个运行应用、正向交易、支付、履约、不可变地址与价格快照、营销权益生命周期、真实中间件冒烟和67个自动测试。

该基线后续不得被专项实验破坏。每个阶段结束都必须回归正向交易和未支付取消链路。

### M1：整单退货退款闭环

目标：完成第一条完整逆向交易链，并验证跨 Trade、Fulfillment、Inventory、Payment 的最终一致性。

首版范围：

- 只支持整单退货退款。
- 不支持部分退款、仅退款、换货和同一订单多次售后。
- 只允许符合状态和时限的已签收/已完成订单申请。
- 退款金额读取下单时价格、优惠和商品行分摊快照，不重新执行当前营销规则。
- 首版退款不自动返还已核销优惠权益；后续以独立营销政策扩展。
- 当前未建模运费、税费和跨币种，退款上限为订单实际支付金额。

领域所有权：

| 服务 | 新增责任 |
| --- | --- |
| Trade | 售后单、售后项快照、审核、售后状态历史和最终完成 |
| Fulfillment | 退货单、寄回信息、仓库收货、验收结果和证据 |
| Inventory | 以售后单号幂等回补库存并写库存流水 |
| Payment | 退款单、渠道请求、回调、退款流水和退款结果 |

推荐事件链：

```text
AfterSaleApproved
  -> ReturnReceiptCreated
  -> ReturnReceived
  -> ReturnInspected
  -> ReturnStocked
  -> RefundRequested
  -> RefundSucceeded / RefundFailed
  -> AfterSaleCompleted
```

关键约束：

- 同一订单首版最多一笔整单售后，数据库唯一约束兜底。
- 库存回补业务键至少包含 `afterSaleNo + skuId`，重复事件只产生一条有效流水。
- Payment 以 `afterSaleNo` 幂等创建一笔退款单，退款累计金额不得超过成功支付金额。
- 仓库验收与渠道退款是两个独立事实，不通过回滚远程状态解决失败。
- 库存已回补但退款暂时失败时，保留 `REFUND_PROCESSING/REFUND_FAILED` 并重试或人工处理，不反向扣减库存。
- Trade 只在消费明确的退款成功事实后完成售后。

退出条件：

- 单元与集成测试覆盖全部合法/非法状态迁移。
- 重复申请、重复验收、重复回补、重复退款请求和重复退款回调均无重复副作用。
- 退款渠道超时显示处理中，恢复后能够收敛。
- RocketMQ 中断后恢复，Outbox 能继续推进售后。
- 正向交易、取消、营销核销和履约回归通过。
- 真实 MySQL、RocketMQ 和模拟支付渠道端到端冒烟通过。

### M2：可观测性、韧性与补偿治理

目标：把分散在日志和定时任务中的恢复能力提升为可观测、可告警、可操作的系统能力。

实施范围：

- 为同步 HTTP 调用建立连接、读取和总请求超时预算。
- 为关键依赖建立熔断、并发舱壁和降级规则。
- 只对明确幂等、可安全重试的调用执行有限退避重试。
- 统一传播 `traceId/requestId/eventId/orderNo/afterSaleNo/refundNo`。
- 接入指标采集、链路追踪和结构化日志。
- 建立 Gateway、HTTP客户端、数据库连接池、Outbox、MQ消费、恢复任务和业务处理中数量指标。
- 建立只读聚合、领域授权重试的补偿工作台；禁止中央服务跨库改数据。
- 建立退款、支付、订单、库存和履约的对账任务。

最低观测指标：

```text
HTTP 请求量、错误率、P50/P95/P99
下游超时、熔断开启、舱壁拒绝
数据库连接池使用率、慢查询、锁等待
Outbox 最老未发布时长、待发布数量、失败次数
MQ 消费延迟、重试次数、死信数量
PENDING_STOCK、CANCELING、REFUND_PROCESSING 等中间态数量与年龄
```

退出条件：

- 一笔订单和一笔退款可以跨 HTTP 与 RocketMQ 查看完整链路。
- 关闭任一非最终事实中间件不会产生伪成功。
- 下游持续超时不会耗尽调用方线程或连接。
- 超过阈值的处理中业务可以告警并在工作台定位。
- 人工重试拥有权限校验、幂等保护和审计记录。

### M3：应用容器化、多实例与发布治理

目标：从“单机运行多个独立服务”升级为“可重复部署和验证的多实例集群”。

实施范围：

- 为 Gateway 和业务服务提供统一、最小化、非 root 的容器镜像。
- Compose 支持按 foundation、transaction、collaboration、campaign 配置组启动。
- 至少对 Gateway、Trade、Inventory、Payment 启动两个实例验证。
- 验证服务发现、负载均衡、无状态认证和消费者组竞争。
- 定时任务使用数据库抢占、租约或等价机制，避免多实例重复处理。
- 支持优雅停机、消费者停止拉取、在途请求完成和健康探针。
- 验证新旧接口和事件版本同时存在时的兼容性。
- 建立滚动升级和失败回滚脚本；灰度或蓝绿在此基础上实现。

故障场景：

- 在本地事务提交后、Outbox 发布前终止进程。
- 在 MQ 发送成功、发布状态更新前终止进程。
- 在消费者完成业务事务、确认消息前终止进程。
- 在库存预占成功、HTTP 响应返回前断开网络。
- 滚动停止一个实例，验证请求和消费继续进行。

退出条件：

- 全栈可从干净环境按文档启动。
- 多实例并发不产生重复订单、库存、支付、退款或履约单。
- 任一应用实例退出后关键业务最终恢复。
- 发布过程中健康实例持续提供服务，失败版本可回滚。

### M4：素简记顾客端与管理端 V1

目标：把已经完成的后端能力交付为现代、完整、可理解的产品体验。

顾客端范围：

- 注册、登录、个人资料和地址。
- 首页、分类、商品列表、商品详情和媒体展示。
- 购物车、结算、优惠选择、价格明细和订单提交。
- 支付状态、订单列表、订单详情和取消。
- 履约进度、物流时间线、签收和售后申请。
- 优惠权益列表和使用状态。

管理端范围：

- 内部账号与权限入口。
- 类目、品牌、SPU、SKU、媒体和上下架。
- 仓库、库存调整、库存流水和预占查询。
- 订单、支付、履约、物流和售后处理。
- 营销规则、权益发放和锁定/核销查询。
- 补偿、对账、审计和系统健康工作区。

工程与体验验收：

- 建立颜色、字体、间距、圆角、阴影、动效和状态语义设计令牌。
- 关键流程拥有加载、空、失败、处理中、重试和权限不足状态。
- 顾客端完成桌面响应式，并保证主要移动宽度可用。
- 金额使用统一格式，优惠和退款能够追溯到商品行。
- 建立组件测试、关键流程 E2E、构建检查和基础可访问性检查。
- 不复用或模仿既有项目前端的视觉资产与布局。

### M5：容量基线与普通业务高并发优化

目标：先量化单机容量和瓶颈，再实施缓存与资源治理，避免凭感觉宣称高并发。

实施步骤：

1. 固定硬件、JVM、容器资源、数据量和压测模型。
2. 建立商品查询、购物车、结算、普通下单、支付回调和订单查询脚本。
3. 记录吞吐、P50/P95/P99、错误率、CPU、内存、GC、连接池、慢查询、锁等待和 MQ 积压。
4. 根据基线优化 SQL、索引、连接池和线程池。
5. 为 Catalog 建立本地缓存 + Redis 的多级缓存示范。
6. 实现空值缓存、TTL 随机打散、热点互斥/逻辑过期和事件失效。
7. 验证缓存重建、热点 Key、Redis 故障和缓存一致性。
8. 按证据决定是否增加读副本或资源隔离。

正确性底线：

- 库存 100、并发 1000 次预占，成功不超过 100，库存不为负。
- 同一幂等键并发提交 100 次，只创建一个订单。
- 同一支付或退款回调并发提交 100 次，只产生一个有效结果。
- MQ 事件重复投递 10 次，副作用只发生一次。
- 所有性能报告同时给出错误率和业务正确性，禁止只展示 QPS。

退出条件：

- 压测脚本、数据生成器、监控面板和报告可重复执行。
- 优化前后结果使用同一环境和负载模型对比。
- 明确记录个人机器的稳定容量、拐点、瓶颈和扩容建议。

### M6：秒杀与峰值流量体系

目标：建立独立于普通下单入口的高并发活动链路，并证明峰值不会拖垮普通交易和退款。

流程：

```text
客户端节流与风险校验
  -> Gateway 活动限流
  -> Redis Lua 原子准入与一人一单
  -> RocketMQ 排队削峰
  -> 消费者幂等创建订单
  -> MySQL 最终库存裁决
  -> 结果查询与超时释放
```

实施范围：

- 活动和 SKU 预热、准入量和活动状态。
- Redis Lua 原子资格校验，不把 Redis 数量作为最终库存。
- 请求令牌/结果查询，避免客户端持续重试创建订单。
- 秒杀 Topic、消费者线程池和普通交易资源隔离。
- MQ 积压、消费速率、预计清空时间和死信告警。
- Redis 不可用时秒杀快速失败，普通下单继续使用 MySQL 裁决。
- 防重复、一人一单、热点用户和热点 SKU 保护。

退出条件：

- 秒杀峰值下不超卖、不重复下单。
- 普通下单、支付和退款的延迟与可用性保持在事先定义的水位内。
- MQ 堆积、消费者重启和 Redis 故障后结果最终可核对。
- 输出容量曲线和资源隔离前后对比报告。

### M7：数据规模化专项

目标：选择订单与商品查询两个代表性领域，完整实践数据规模扩展，而不是全服务形式化分片。

实施范围：

- 建立全局业务 ID 方案，验证多实例唯一性和时钟/号段异常。
- 为 Catalog 查询搭建真实 MySQL 读副本，验证复制延迟和读己之写策略。
- 生成百万级并逐步推进至个人机器极限的数据集，记录存储与索引成本。
- 对 Trade 的订单、订单项、快照和分摊表设计一致的分片键与路由。
- 解决跨表同路由、按用户分页、按订单号定位和后台跨分片查询。
- 实践历史订单归档、在线迁移、扩容和回滚。
- 保留分片前后的相同业务契约和回归测试。

退出条件：

- 分片不是只完成配置，必须跑通下单、查询、支付、履约和退款。
- 能解释无法高效支持的跨分片查询以及替代方案。
- 迁移过程有校验、断点、回滚和数据核对记录。
- 输出单表、读写分离和分片方案的量化对比。

### M8：协作、实时与内容能力

目标：补齐现代电商的实时交互和内容闭环，并实践与交易不同的系统模型。

范围：

- `chat-service`：顾客与平台客服会话、客户端消息幂等、已读未读、离线消息和附件。
- `notification-service`：站内信、邮件、模板、重试和发送记录。
- 物流定位：MySQL 保存关键轨迹，Redis GEO 保存最新位置，前端地图展示。
- 商品评价：订单完成资格、评价、回复、点赞、举报和媒体。
- 搜索：商品索引、增量更新、重建与数据库事实核对。
- 运营统计：从事件或只读模型生成，不跨服务直接 JOIN 生产表。

退出条件：

- 消息持久化后才向发送方确认成功，断线重发不重复。
- 多个 WebSocket 节点可以路由在线用户，节点退出后能够转离线。
- Redis GEO 丢失不影响关键物流事实。
- 搜索索引可以重建，错误索引不会改变商品真实状态。

### M9：多商户平台演进

进入条件：

- 自营正向、逆向交易稳定。
- 支付退款与库存能够对账。
- 多实例、观测、压测和前端主流程完成。
- 已明确多商户是业务扩展，不是简单给所有表增加 `tenant_id`。

第一阶段范围：

- Merchant、Shop、商户状态和平台审核。
- 商户子账号及店长、客服、仓库角色。
- 商品、SKU、仓库和库存的经营主体归属。
- 顾客提交父订单，按店铺拆分子订单和履约责任。
- 平台优惠与店铺优惠的规则、成本归属和商品行分摊。
- 支付成功后的平台账本、商户应结算金额、手续费和佣金。
- 店铺级发货、售后审核、退货仓和逆向结算。
- 平台跨商户监管与商户数据权限测试。

关键原则：

- `merchantId/shopId` 首先是业务所有权，不机械等同于 SaaS 租户。
- 消费者跨店搜索和平台监管不能被全局租户过滤器破坏。
- 支付渠道是否真实分账可以分阶段，但内部账本必须守恒、可对账。
- 父订单、子订单、支付单、结算单和退款单拥有独立状态机。
- 多商户改造不得破坏已有自营模式，自营平台可作为一个特殊经营主体兼容。

退出条件：

- 两个商户的商品可在同一购物车结算并正确拆单。
- 平台券、店铺券、补贴和实付按商品行及资金承担方精确核对。
- 商户无法查询或操作其他商户的商品、订单、售后和结算。
- 部分店铺发货、退款或异常不会错误推进其他子订单。
- 平台账本、商户结算和逆向退款保持借贷/收支守恒。

### M10：最终交付与毕业验收

交付物：

- 可重复构建的后端和前端源码。
- 数据库迁移、测试数据生成和环境引导脚本。
- 全栈容器化与分组启动方案。
- 单元、集成、契约、E2E、真实中间件、故障注入和压测脚本。
- 架构、状态机、事件目录、运行手册、故障手册和容量报告。
- 顾客端、管理端、治理工作台和演示账号。
- 已知限制、技术债和下一阶段演进说明。

毕业标准：

1. 正向交易、逆向退款和多商户最小链路均可演示和自动验证。
2. 重复、乱序、延迟消息及服务退出不会制造重复资金或库存副作用。
3. 任一处理中状态都能解释其原因、恢复路径和人工介入方式。
4. HTTP 与 MQ 链路可追踪，关键积压和异常可告警。
5. 高并发结论有固定环境、压测脚本和数据报告支撑。
6. 数据扩展方案经过真实迁移和回归，不停留在架构图。
7. 前端保持素简记的现代极简设计，同时完整呈现交易事实。
8. 新开发者可以依照文档从干净环境启动、测试和定位故障。

## 12. 主要风险与控制方式

| 风险 | 控制方式 |
| --- | --- |
| 为学习堆砌技术 | 每项技术绑定业务场景、失败复现和验收证据 |
| 多条主线同时展开 | 每个里程碑指定一个主工作流，限制在制品数量 |
| 微服务变成分布式单体 | 强制数据所有权、禁止跨库 JOIN、控制同步调用环 |
| 重试制造重复副作用 | 先设计幂等键、唯一约束和结果查询，再允许重试 |
| 缓存成为最终事实 | 所有缓存可丢失、可重建，数据库能够独立裁决 |
| 压测只追求 QPS | 同时验证错误率、P99、库存、资金和消息收敛 |
| 分库分表污染全项目 | 只选代表领域，保留未分片契约和回退方案 |
| 多商户权限越界 | 平台与商户权限分层，建立跨商户攻击测试 |
| 前端简洁导致信息缺失 | 关键交易事实始终可见，使用渐进披露而非隐藏 |
| 单机资源不足 | 分组启动、限制容器资源、记录硬件和缩比边界 |
