# 当前产品范围

## 1. 产品定位

本项目定位为单平台自营 B2C 电商，不引入商家入驻、平台抽佣、商家结算等多主体
复杂度。目标不是复制大型平台的功能数量，而是围绕一条完整交易链验证分布式、高并发
和最终一致性。

该范围已经作为 M0-M8 完整参考基线关闭，不是等待多商户能力补齐的临时版本。
多商户、平台账本和结算进入独立
[PlainJournalPro](https://github.com/NoctilumeDev/PlainJournalPro)；两个仓库的控制组
关系与验证边界见[参考基线与 Pro 边界](reference-baseline-and-pro-boundary.md)。

核心闭环：

```text
浏览商品 -> 加入购物车 -> 确认订单 -> 预占库存 -> 支付
-> 仓库履约 -> 物流追踪 -> 确认收货 -> 评价 / 售后
```

客服会话可以从商品、订单和售后单进入；通知服务贯穿支付、发货、物流和售后状态变化。

## 2. 使用角色

| 角色码 | 当前交付与入口边界 |
| --- | --- |
| `CUSTOMER` | 顾客商城：注册登录、浏览、购物车、下单、支付、查看物流、评价、售后、联系客服 |
| `OPERATOR` | 管理端运营工作区：商品、类目、品牌、营销活动和内容维护 |
| `WAREHOUSE` | 管理端仓库工作区：库存、履约、发货和异常处理 |
| `ADMIN` | 管理端跨工作区访问；内部账号开通与角色分配仍依赖受控引导，未提供完整账号、权限和系统配置管理界面 |
| `CUSTOMER_SERVICE` | 已预置角色码；客服会话接口与 Chat 工作区已有实现，但管理端登录尚不接受仅有该角色的账号 |
| `FINANCE` | 已预置角色码；支付、退款、对账功能存在，未交付独立财务登录与工作区，不能把角色预置等同于入口完成 |

顾客账号与内部员工账号共享统一身份认证能力，但权限模型、登录入口和风控策略分开。

## 3. 前端入口

| 应用 | 定位 |
| --- | --- |
| `storefront-web` | 顾客商城，优先完成桌面响应式页面 |
| `admin-web` | 由 `ADMIN`、`OPERATOR` 或 `WAREHOUSE` 进入授权工作区 |
| 客服工作台 | `admin-web` 中的 Chat 工作区；进入规则仍受管理端角色准入约束 |

管理端会按角色限制路由与操作；精确准入、受控员工引导和认证边界见
[身份与账号安全](08-identity-security.md)。角色名称不能作为某个后台入口已完成的证据。

当前不开发独立骑手 App。物流坐标由模拟上报端或测试脚本产生，真实承运商通常只提供
轨迹节点，不提供持续 GPS。

## 4. 当前业务能力

### 身份与账号

- 顾客注册、登录、刷新令牌、退出与收货地址；密码重置尚未实现。
- 预置内部角色、受控员工账号引导、后端接口授权与前端工作区/操作限制；没有完整的账号、角色、菜单和按钮权限配置后台。
- 登录限流、失败锁定、JWT/刷新令牌和审计日志。

### 商品与库存

- 类目、品牌、SPU、SKU、价格、图片和上下架。
- 多仓库存账、可用库存、预占、确认扣减、释放和流水。
- 商品详情与库存展示允许缓存，但数据库保留最终事实。

### 交易与支付

- 购物车、结算预览、订单创建、取消、超时关闭、订单查询。
- 当前使用可替换的模拟支付渠道，仍完整实现签名、回调幂等和退款状态机。
- 订单保存商品、价格和地址快照，后续商品修改不能改变历史订单。

### 营销价格基础

- 优惠券、红包、补贴各最多使用一份，三种类型允许叠加。
- 优惠规则支持按省、市、区六位行政区划编码限制可用地区。
- 下单锁定权益，订单取消或缺货关闭后释放，支付成功后核销。
- 订单保存原价、分类优惠、实付金额以及逐权益逐订单项分摊快照。

### 履约、物流与售后

- 仓库拣货、打包、发货和运单创建。
- 物流时间线、最新位置、异常节点和用户侧进度展示。
- 退款、退货退款、审核、退货入库和退款完成闭环。

### 客服与通知

- 顾客与平台客服一对一会话。
- 文本、图片和文件附件，消息已读未读、离线消息和历史记录。
- 会话可绑定商品、订单或售后单，但只能通过服务 API 校验访问权。
- 站内信为必做；邮件作为补充渠道，发送失败进入补偿任务。

## 5. 已完成的增强能力

- 满减、限时活动、自动领取/发放活动和多类权益分摊。
- 秒杀专用入口、Redis Lua 准入、异步排队和结果查询。
- OpenSearch 商品检索、MySQL 降级、蓝绿重建和版本对账。
- Prometheus、Alertmanager、Grafana 和 Tempo 代表观测链路。
- Chat、通知、附件扫描、物流 GEO、商品评价和运营统计。
- 三实例竞争、滚动发布、读副本、分片、归档和主动重分片代表实验。

## 6. 明确不做

- 多商家入驻、店铺结算和平台抽佣。
- 直播、短视频、广告竞价和复杂推荐算法。
- 跨境税费、多币种和国际仓。
- 真实支付渠道、真实承运商、持续 GPS、外部地图和独立骑手 App。
- 将 Redis 库存当成最终库存，或依赖分布式锁保证最终正确性。
- 为了形式完整而一次启动全部服务；本地按功能配置分组运行。

以上“不做”是当前仓库的所有权边界，不表示能力缺失。M9 及以后的平台化设计必须在
PlainJournalPro 中重新定义经营主体、父子订单、账本和结算状态机。

## 7. 验收主线

1. 顾客选择 SKU 并提交订单。
2. 库存只有 1 件时，并发请求最多成功 1 个，库存不为负。
3. 支付回调重复到达，只产生一次有效支付结果。
4. 未支付订单到期关闭并释放预占库存。
5. 支付成功触发履约，发货后顾客能看到物流节点。
6. 顾客可从订单进入客服会话并收到回复及未读提示。
7. 售后完成后退款、订单、库存和流水可以相互核对。
