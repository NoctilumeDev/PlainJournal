# M5 容量方法与第一批基线

> 日期：2026-07-21  
> 状态：本文件记录 M5 第一批方法基线；查询容量、写链容量、Catalog 缓存治理及 M0–M7 最终复验均已完成

## 1. 目标与回归原则

M5 不以单个高 QPS 数字为目标，而是回答四个问题：

1. 当前单机在固定数据量和固定资源下的稳定容量是多少；
2. 首个明显拐点来自应用、数据库、Redis、RocketMQ 还是宿主机；
3. 一项优化是否同时改善吞吐、尾延迟和业务正确性；
4. 优化是否破坏 M0 至 M4 的事务、幂等、补偿、对账或结果未知恢复。

执行采用两层门禁：

- 每个 M5 小切片运行定向自动化、对应真实中间件场景和局部压测；
- M5 收口时完整重跑 M0 至 M5：后端/前端门禁、五中间件正逆向链、同步韧性、四域对账、三类结果未知、多实例/发布治理、1000 并发正确性，以及 M5 新增容量曲线、缓存故障、背压和资源隔离。

## 3. HTTP 负载执行器

新增无第三方依赖的 Node.js 执行器：

```powershell
node .\tools\m5-http-load-runner.mjs `
  .\tools\m5-load-config.example.json `
  .\.run\m5-catalog-list.json
```

配置支持：

- 总请求数、并发数、预热请求数和单请求超时；
- 多场景权重；
- HTTP 方法、URL、Header 和 JSON Body；
- 期望 HTTP 状态、顶层 JSON `code` 和响应文本；
- `${ENV:VARIABLE_NAME}` 环境变量替换，避免把访问令牌写入版本库；
- 最大允许错误率。

证据统一输出：

- 请求数、成功数、传输错误、响应契约错误和错误率；
- P50、P95、P99、最小、最大和平均延迟；
- 吞吐、状态码分布和响应字节数；
- 总体与各场景明细；
- 最多 20 条错误样本；
- Node 版本、参数、UTC 时间和最终通过状态。

自动化：

```powershell
node --test .\tools\m5-http-load-runner.test.mjs
```

当前 3 个测试通过，覆盖加权并发场景、吞吐/分位数统计、响应契约失败计数和 URL 池轮转。

## 5. 正式基线模型

后续正式曲线使用同一份数据和相同请求组合，初始数据层级控制在 M5 范围，不提前进入 M7 数据规模化：

| 数据 | 第一层目标 |
| --- | ---: |
| ACTIVE SPU | 1,000 |
| ACTIVE SKU | 3,000 |
| 顾客账户 | 1,000 |
| 每个顾客购物车行 | 3 |
| 历史订单 | 10,000 |
| 可支付测试订单 | 按压测批次独立生成 |

每个场景先预热，再按并发 `1 / 5 / 10 / 20 / 50 / 100` 逐级执行；每个水位至少重复三次。进入下一水位前必须满足：

- 传输错误率和非预期业务错误率在预定水位内；
- P99 没有持续失控；
- MySQL 连接、锁等待和慢查询可解释；
- JVM 没有持续 Full GC 或 OOM；
- RocketMQ 积压能够在业务截止时间内排空；
- 库存、订单、支付和退款幂等断言成立。

正式场景顺序：

1. Catalog 列表与详情；
2. 购物车查询与更新；
3. 结算试算；
4. 普通下单；
5. 支付回调；
6. 订单列表与详情；
7. 混合读写模型。

## 6. 第二批执行结果

确定性数据生成、固定应用资源、Catalog/Trade 查询曲线和 Trade 订单列表优化已经完成。正式对比使用：

- 1,000 ACTIVE SPU、3,000 SKU；
- 1,000 顾客、3,000 购物车行；
- 10,000 历史订单，其中一个顾客持有 1,000 单；
- 256 MiB 固定堆、4 个活动处理器、20 个 Hikari 连接、100 个 Tomcat 工作线程；
- 并发 `1 / 5 / 10 / 20 / 50 / 100`，每个水位三次、每次 1,000 请求；
- Catalog 列表/详情和 Trade 购物车/订单列表/订单详情均经真实 Gateway、Nacos 和 MySQL。

最终正式曲线共 39 个运行、36,003 个请求、0 错误。Trade 订单列表从无分页且每单分别读取商品行、地址、价格快照和优惠分摊，改为：

- 新增 `/api/v1/trade/orders/page`，默认 20、最大 100；
- 订单页子表按订单 ID 集合批量读取，查询次数不再随订单数线性增长；
- `/api/v1/trade/orders` 保留数组响应并限制最近 100 单，兼容滚动窗口中的旧前端；
- 顾客端使用分页响应和“加载更多”，不会把分页对象误当数组；
- 正式编排在每个受保护场景前刷新短期 JWT，避免长曲线把认证过期误判为容量失败。

- 39 份 Trade Hikari 采样的连接超时累计值均为 0；

## 7. 尚未得出的结论

当前不能宣称：

- Catalog 稳定容量为 604.95 RPS；
- 需要立刻增加数据库连接数或 JVM 堆；
- MySQL/Nacos/RocketMQ 接近内存限制就是内存泄漏；
- Redis 缓存一定能改善尾延迟；
- 读副本、分库分表或更多实例已经有进入依据。

当前测试上限内 Catalog 和优化后的 Trade 仍未出现错误，但不能把并发 100 直接称为最终容量上限，也不能据此推导生产硬件容量。写链与 Catalog 缓存切片的正式结果见 [M5 写链容量与 Catalog 多级缓存](43-m5-write-capacity-and-catalog-cache.md)；M5 总收口仍需基线移除和 M0 至 M5 全量复验。
