# Catalog 缓存重建租约维护

基于 `798b1b21a5734be3403635484b023fd51ec10259` 的局部候选，仅修改 Catalog 缓存写回和对应回归入口。

## 失败机制

实例 A 取得重建锁并开始读取旧快照；A 的锁过期，实例 B 取得新锁并写入新值；A 未收到失效通知，随后恢复。原实现只在释放锁时核对令牌，缓存写回仍为无条件 SET，因此 A 能把 B 的新值覆盖为旧值。本地失效代数只能处理已收到的通知，不能替代共享锁所有权。

## 当前处理

- Redis Lua 将“锁令牌仍属于本任务”和“写入缓存及 TTL”放在一次原子操作中。过期、丢失或被替换的令牌均不能写回；空结果缓存也遵守同一条件。
- 原本取得过锁的重建任务，只有共享写入获准后才将本次结果放入本地缓存。核对失败或 Redis 调用结果不确定时，仅返回本次数据库读取，不缓存这份结果。
- 获取锁时 Redis 已不可用，继续保留有容量限制的数据库/本地降级，但不会在 Redis 中途恢复后无令牌写入共享缓存。
- 失效代数、有限等待、重建容量限制、正常 TTL、异步刷新及令牌匹配解锁继续生效。

这里不把商品缓存升级为线性一致性存储。变更前已经开始的请求仍可能返回其读取的旧快照；正常逻辑过期、本地降级和通知丢失的已有时间边界继续存在。修复证明的是**失去重建租约的任务不能再覆盖共享缓存**，不证明任意 Redis 故障转移或所有通知组合都没有陈旧读取。订单等业务事实仍应由其原有数据库合同裁决。

## 复验

回归使用独立 Redis 7.4.9、两个真实缓存实例及一个独立读实例。数据库快照和 Pub/Sub 是否送达是受控输入，不冒充真实 MySQL 或完整消息链路验收。

真实 Redis 检查覆盖：旧令牌不能释放新锁、原子写入与 TTL、过期且无继任者、继任者持锁、收到/漏收通知后的旧加载，以及旧空结果不能隐藏新商品。单元回归另覆盖 Redis 在读取期间恢复、写回核对故障、正常合并加载、容量保护、刷新与失效。

在本机隔离 Redis 已启动后，执行（示例端口 26379）：

```sh
cd backend
./mvnw -pl services/catalog-service -am -Dcatalog.redis.test.port=26379 clean verify
```

真实 Redis 用例仅在指定端口时运行，并只清理带随机命名空间的自有键；没有端口则明确跳过。候选 CI 在原 `Backend verify` 中配置专用 Redis 服务并传入端口，使这些用例在该检查中实际运行。

本地 Catalog 及 platform-common 共 79 项测试通过（含 5 项真实 Redis 测试），模块既有覆盖率门槛通过。这个结果不替代全仓 CI 或合并后主线核验，也不改写历史验收记录。
