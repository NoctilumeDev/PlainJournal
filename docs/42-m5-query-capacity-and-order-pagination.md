# M5 查询容量、订单分页与 N+1 收敛

> 日期：2026-07-21  
> 状态：M5 第二批完成；第三批写链与 Catalog 缓存证据见 [M5 写链容量与 Catalog 多级缓存](43-m5-write-capacity-and-catalog-cache.md)

## 1. 结论

固定数据与固定资源下的第一条正式查询曲线已经完成。Catalog 在测试上限内没有错误；Trade 首个明确瓶颈不是 JVM 堆、Hikari 数量或 Redis，而是订单列表的无界响应和 N+1 查询。

本批没有通过调大资源掩盖问题。固定参数始终为：

| 项目 | 值 |
| --- | ---: |
| JVM 堆 | 256 MiB |
| 活动处理器 | 4 |
| Hikari 最大连接 | 20 |
| Tomcat 最大线程 | 100 |
| 每次负载请求 | 1,000 |
| 重复次数 | 3 |
| 并发阶梯 | 1 / 5 / 10 / 20 / 50 / 100 |

最终正式结果为 39 个运行、36,003 个请求、0 个传输或响应契约错误。

## 3. 优化前基线

优化前的 39 组正式曲线全部通过，但暴露两个问题：

1. Trade 混合查询在并发 20 后吞吐基本停在约 1,000 RPS，尾延迟继续上升；
2. 1,000 单顾客的一次订单列表请求需要 1830.44–2102.00 ms。

代码路径为：

```text
查询顾客全部订单
  -> 对每笔订单调用 view()
     -> 查询订单行
     -> 查询地址快照
     -> 查询价格快照
     -> 查询优惠分摊
```

普通约 10 单顾客需要约 41 次查询；1,000 单顾客需要约 4,001 次查询。连接池没有超时，说明增加连接数不会消除该查询放大。

## 4. 代码收敛

### 4.1 有界分页

新增：

```text
GET /api/v1/trade/orders/page?page=1&size=20
```

- 默认每页 20；
- 最大每页 100；
- 返回 `items / page / size / total`；
- 以 `created_at DESC, id DESC` 保持稳定顺序。

旧端点：

```text
GET /api/v1/trade/orders
```

继续返回数组，并限制为最近 100 单。这样旧前端在滚动窗口内不会把分页对象当数组而崩溃；新前端使用分页端点和“加载更多”。

### 4.2 批量加载

订单页先取得有界订单 ID 集合，再各执行一次批量查询：

- 订单行；
- 地址快照；
- 价格快照；
- 优惠分摊。

因此一页的查询数量保持常数级，不再随订单数按四倍线性增长。单订单详情继续使用原来的精确读取，不改变详情和结果未知恢复契约。

### 4.3 编排修复

第一次优化后正式复测在第 35 个运行失败，1000 个请求全部返回 401。原因是完整曲线超过访问令牌有效期，脚本在启动时只登录一次。

这批结果没有计入成功证据。编排改为每个受保护场景前刷新普通顾客 JWT，密集用户场景同时刷新密集顾客 JWT。最终重跑 39/39 全部通过，Identity/Catalog 的 1,248 项指标采集也全部为 HTTP 200。

Catalog 最终曲线在并发 100 的中位吞吐为 1576.72 RPS，最差 P95 为 90.14 ms，0 错误。测试没有继续提高并发，当前不能宣称 1576.72 RPS 是最终容量上限。
