# PlainJournal 参考基线与 Pro 边界

> 决策日期：2026-08-06  
> 适用范围：PlainJournal `v1.0.x`、后续前端视觉版本，以及独立仓库
> [PlainJournalPro](https://github.com/NoctilumeDev/PlainJournalPro)

## 1. 决策摘要

PlainJournal 是已经闭环的 M0-M8 自营 B2C 参考基线，不是功能残缺的 Basic 版，也不是
等待多商户模块补齐后才算完成的半成品。

当前仓库在 16GB Windows 单机约束下，使用分组启动、控制变量、真实中间件、代表服务
多实例、故障注入、浏览器链路和一致性核对，验证缩比但真实的问题类型。容量结论只对
文档声明的硬件、拓扑、数据和并发模型负责，不外推为生产集群容量。

多商户、父子订单、平台账本、佣金、结算和 Java/Go 异构协作属于 M9 及以后，进入
独立仓库 PlainJournalPro。Pro 以本仓库的业务不变量和验证方法为控制组，但不在当前
Git 历史中直接追加商户字段，也不机械复制全部源码。

## 2. PlainJournal 的冻结范围

PlainJournal 保留以下完整能力：

- M0-M8 自营正向交易、履约、售后、退款、评价、客服、通知、搜索和运营统计闭环；
- 服务数据所有权、本地事务、Outbox、RocketMQ、幂等消费、补偿与对账；
- 结果未知恢复、三实例代表验证、滚动发布、故障治理和数据规模化实验；
- 顾客端、管理端、真实浏览器、F12/CDP、响应式布局和静态发布链路；
- 自动化测试、真实基础设施脚本、发布门禁、文档和开源治理。

冻结规则：

1. `v1.0.x` 只修复明确缺陷、安全问题、依赖风险和工程边界；
2. 不再主动增加大型业务域或为了展示技术而增加中间件；
3. 后续前端视觉版本可以重构样式、布局和交互层级，但不得改变数据所有权、接口语义、
   交易状态机或一致性规则；
4. 当前仓库继续作为 PlainJournalPro 的可重复控制基线，而不是被 Pro 原地改造成
   多商户系统。

## 3. 单机验证方法

### 3.1 约束声明

参考环境是 16GB Windows 单机。每次真实实验必须记录启用的服务、中间件、实例数、
数据规模、并发模型、持续时间和资源占用，并为宿主机、Docker/WSL、JVM 和网络代理
保留余量。

测试编排必须做到：

- 启动前检查内存、端口、容器、代理和残留进程；
- 为每批服务设定资源预算，达到软阈值后停止升压；
- 达到硬阈值时中止测试并保存证据，不用系统失稳换取更大的数字；
- 每批结束后确认进程、端口、容器、连接和临时数据已经释放；
- 不让上一批残留污染下一批结论。

具体软硬阈值由当次环境快照确定，不把固定可用内存数字写成对所有机器都成立的常量。

### 3.2 验证层级

验证按以下顺序执行：

1. **单变量串行**：一次只引入一个主要中间件或故障条件，建立因果基线；
2. **业务 Profile 组合**：按交易、履约、内容、沟通和治理等代表链路组合必要组件；
3. **确定性高风险组合**：覆盖库存、幂等、支付、退款、Outbox、消费恢复和多实例竞争；
4. **带种子的随机顺序**：在确定性用例通过后改变批次、启动和请求顺序，种子必须保存；
5. **代表性全链路验收**：在资源允许的最大有效组合上复跑角色、浏览器、故障、恢复和
   最终对账。

PlainJournal 不宣称在 16GB 单机上对所有中间件、实例数和故障模式做全笛卡尔积并行
压测。单变量用于证明因果，代表组合用于验证交互，随机顺序用于发现偶发问题。

### 3.3 “1000”的解释

“1000”不是一个可以脱离场景使用的统一性能标签。

当前公开验证基线是 **1000 个请求、100 并发**，精确事实以
[验证摘要](verification-summary.md) 为准。后续报告必须分别声明：

- 热点库存、同幂等键或重复回调：总请求数、同时在途请求数和唯一有效副作用数；
- 普通查询与完整业务链：总操作数、并发阶梯、吞吐、延迟和资源拐点；
- WebSocket/Chat：连接数、消息速率、在线时长和重连模型；
- 若报告写“1000 个竞争请求”，必须有对应脚本和结果文件，不能用“共发送 1000 次”
  替代“1000 并发”。

若未来补充专项升压，建议阶梯为
`1 -> 10 -> 50 -> 100 -> 300 -> 500 -> 1000`。每一级先核对业务不变量和资源余量，
再决定是否进入下一级；硬件限制可以终止升压，但不能降低一致性判定标准。

## 4. 一致性退出条件

任一并发、故障或恢复实验只有同时满足以下条件才算通过：

- 库存不为负，库存预占、确认、释放和回补能够对账；
- 同一幂等键只产生一个权威业务结果；
- 重复支付或退款回调不产生重复资金副作用；
- MQ 重复、延迟、乱序或恢复投递不产生重复业务副作用；
- 订单、支付、履约、退款、营销和库存事实最终收敛；
- Outbox、消费失败和补偿记录能够恢复或进入明确人工治理状态；
- 不存在无法解释的永久处理中记录；
- 测试结束后没有业务脏数据、临时对象、端口、JVM 或容器残留。

压测工具显示请求完成不等于业务通过。容量数字必须和数据库事实、消息收敛、日志、
指标及清理结果一起解释。

## 5. 中间件降级边界

每个中间件至少区分完全不可用、响应变慢、间歇失败、已执行但响应丢失，以及重启后
重复投递或状态恢复五类故障。

统一原则是：

> 核心事实不可降级，辅助能力可以有界降级；一致性不可降级，体验可以降级。

- Redis 失败可以回源、限流或关闭增强能力，但不能替代数据库的库存和交易裁决；
- RocketMQ 失败必须由 Outbox 保留业务事实，恢复后继续发布，不能静默丢消息；
- OpenSearch 失败可以退回有限数据库查询或关闭搜索增强，不阻塞交易；
- MinIO、通知、Chat 失败可以延迟附件或沟通能力，不回滚已经成立的交易事实；
- Nacos 故障时，已启动实例和本地配置应在已验证边界内继续运行；
- Metrics、Tracing 或告警通道失败只降低可观测性，不应让核心业务同步失败。

## 6. PlainJournalPro 的职责

[PlainJournalPro](https://github.com/NoctilumeDev/PlainJournalPro) 是 M9 及以后的独立
工程课题，计划在更充足的本机资源下研究：

- Merchant、Shop、商户子账号和经营主体所有权；
- 跨店购物车、父订单、店铺子订单和独立履约责任；
- 平台优惠、店铺优惠、补贴和资金承担方分摊；
- 平台账本、手续费、佣金、商户结算和逆向冲正；
- 店铺级发货、售后、退货仓与跨商户权限隔离；
- Java 交易状态机与 Go 高吞吐、连接密集或批处理服务的明确协作。

Go 必须承担清楚、可独立验证的系统职责，不能为了形成异构架构而机械重写 Java 服务。
候选边界包括实时连接路由、事件聚合、平台账本流水处理或商户结算批处理；最终选择需
由容量、所有权和失败边界决定。

Pro 当前是规划与参考架构仓库，不冒充已经完成的生产系统。未来实现应通过 ADR 记录
哪些 PlainJournal 机制被复用、哪些领域模型必须重建，并保持两个仓库的发布、Issue、
测试证据和 Git 历史独立。

## 7. 两个仓库的关系

| 维度 | PlainJournal | PlainJournalPro |
| --- | --- | --- |
| 业务范围 | M0-M8 单经营主体、自营 B2C | M9+ 多商户平台 |
| 当前状态 | 完整参考基线，业务范围冻结 | 规划与参考架构阶段 |
| 资源边界 | 16GB Windows 单机缩比验证 | 计划在更充足资源下验证 |
| 资金模型 | 顾客与自营平台交易 | 平台、商户、手续费、佣金与结算 |
| 服务演进 | Java/Spring 为主的已验证系统 | Java 交易核心与有职责的 Go 服务 |
| Git 策略 | 保留稳定基线和缺陷修复历史 | 独立建仓，不污染基线历史 |

PlainJournal 的完成不依赖 Pro。PlainJournalPro 的成立也不否定当前仓库，而是以其
已经验证的业务不变量、故障方法和公开证据作为控制组继续演进。
